The four layers, end to end

One request to POST /guides, followed from curl to PostgreSQL and back. Every file here runs in your sandbox.

The stack

  1. 1. API routesrc/api/guides/route.ts: receive, validate, hand off
  2. 2. Workflowsrc/workflows/create-guide.ts: the business logic, with undo
  3. 3. Modulesrc/modules/guide/: owns the guide data
  4. 4. PostgreSQLthe guide table

Subscribers (src/subscribers/) and scheduled jobs (src/jobs/) sit next to the API route as other entry points. They're started by an event or a clock instead of a request. Architecture

LayerIts jobIt must not
API routeSpeak HTTP: read the request, start a workflow, send JSON backHold business rules, or write to several modules itself
WorkflowDecide the steps and their order; undo completed steps on failureRun logic in the constructor (no if, await, loops there)
ModuleOwn one domain's tables and expose a serviceCall another module's service or reference its tables
PostgreSQLStore rows and enforce constraintsBe written to by anything except its module

The happy path: POST /guides

curl -X POST localhost:9000/guides -H "Content-Type: application/json" \
  -d '{"title":"Running shoe sizing","kind":"sizing","body":"Order half a size up."}'
#LayerWhat happens
1Route (middleware)src/api/middlewares.ts matches POST /guides and runs validateAndTransformBody(PostGuideSchema). Zod checks the JSON. Bad body: 400, stop here.
2Route (handler)The file path gives the URL and the export name POST gives the method. The handler calls createGuideWorkflow(req.scope).run({ input }).
3WorkflowMedusa starts the recorded steps in order. create-guide runs first.
4Workflow stepcontainer.resolve("guide") returns the Guide module's service from the container.
5ModulecreateGuides(input), a method generated by MedusaService({ Guide }), builds the insert.
6PostgreSQLINSERT INTO guide ... with an id Medusa generated. The check constraint on kind runs, and the column defaults fill in created_at and updated_at.
7Workflow stepnew StepResponse(guide, guide.id): the guide goes on to the workflow, and the ID is saved for the undo.
8Workflowsimulate-failure passes. emitEventStep queues guide.created. The workflow succeeds, so the event goes out.
9Route.run() resolves to { result }. The handler sends res.json({ guide: result }), which is a 200.
10SubscriberSeparately, guide-created.ts receives { id }, calls retrieveGuide, and logs. If it throws, steps 1 to 9 still stand.

The failure path: ?simulate_failure=true

#What happens
1 to 7Same as above. The row exists in the guide table.
8simulate-failure throws a MedusaError of type NOT_ALLOWED.
9Medusa runs the compensations of finished steps, newest first: deleteGuides(guideId). The row is gone.
10emitEventStep never runs, so there's no event and no subscriber.
11.run() throws, and Medusa answers {"type":"not_allowed", ...} with HTTP 400.

The result: the guide was either created and announced, or it's as if the request never happened. That's what a plain route can't give you across several modules. Lesson 3

The same request with the other two doors

Entry pointStarts itCalls
API routePOST /guidescreateGuideWorkflow(req.scope).run({ input })
SubscriberAn event, e.g. product.createdcreateGuideWorkflow(container).run({ input })
Scheduled jobA cron schedulecreateGuideWorkflow(container).run({ input })

The workflow doesn't know or care who called it. That's why business logic lives there and not in the entry point.

Where your agent fits

Your support agent sits outside this whole stack. It calls Medusa's API routes over HTTP and never reaches a workflow, a module, or the database directly. Each piece of data has one owner, and everything else asks that owner. A tool like request_return sends one HTTP request. Validation, the steps, and the rollback all happen on Medusa's side, inside a workflow.
