Medusa defines a module as "a reusable package of functionalities related to a single domain or integration".[2] Medusa's own features are modules too: Cart, Order, Customer, Product. If you know Django, a module is close to a Django app: its own models, its own logic, its own migrations.

A module is three files

We'll build a small Guide module: sizing, care, and compatibility guides, the kind of content your support agent will one day answer questions from. It lives in its own folder:

src/modules/guide/
├── models/guide.ts    the data model: one table
├── service.ts         the class that reads and writes it
└── index.ts           the module definition: name + service

1. The data model

import { model } from "@medusajs/framework/utils"

const Guide = model.define("guide", {
  id: model.id().primaryKey(),
  title: model.text(),
  kind: model.enum(["sizing", "care", "compatibility"]),
  body: model.text(),
  summary: model.text().nullable(),
})

export default Guide

A data model "represents a table in the database".[2] It plays the same role as a SQLAlchemy or Django model. model.define takes the table name (snake_case) and an object describing the columns. Some details:

  • Property types include id, text, number, boolean, enum, dateTime, json, and bigNumber (for prices).[3]
  • Calls chain: model.text().nullable() is a text column that may be null. Others are .unique(), .default(...), .index(). Each call returns the property, so you can keep adding to it.
  • You never write created_at, updated_at, or deleted_at. Medusa adds them to every model. A soft delete keeps the row and sets deleted_at to the current time.[3]

2. The service

import { MedusaService } from "@medusajs/framework/utils"
import Guide from "./models/guide"

class GuideModuleService extends MedusaService({
  Guide,
}) {
}

export default GuideModuleService

The service is the class that does database work for the module.[2] This one has an empty body, yet it already has a full set of methods. MedusaService({ Guide }) is a function call that returns a class, with generated methods for each model you pass in. Your class then inherits from that generated class.[4]

Generated methodDoes
listGuides(filters), listAndCountGuides(filters)Fetch many records, optionally with a count
retrieveGuide(id)Fetch one record by ID. The only singular name.
createGuides(data), updateGuides(data)Write one record or an array of them
deleteGuides(ids), softDeleteGuides(ids), restoreGuides(ids)Remove, soft-remove, undo a soft remove

The rule: operation name, then the model name, pluralised for everything except retrieve.[2]

3. The module definition

import { Module } from "@medusajs/framework/utils"
import GuideModuleService from "./service"

export const GUIDE_MODULE = "guide"

export default Module(GUIDE_MODULE, {
  service: GuideModuleService,
})

This tells Medusa the module's name and its main service. When the app starts, Medusa registers the service in its container under the module's name.[2] The name can only contain letters, numbers, and underscores. Exporting it as a constant (GUIDE_MODULE) saves you from typing the string by hand later.

Two more things before it works. You list the module in medusa-config.ts (modules: [{ resolve: "./src/modules/guide" }]). Then you create the table with migrations, the same idea as Alembic: npx medusa db:generate guide, then npx medusa db:migrate.[5]

Four new pieces of TypeScript

Python

{"Guide": Guide}

class GuideModuleService(make_service(Guide)):
    pass

# every top-level name is importable
from .service import GuideModuleService

TypeScript

{ Guide }

class GuideModuleService extends MedusaService({ Guide }) {
}

export default GuideModuleService
import GuideModuleService from "./service"
  • { Guide } is shorthand for { Guide: Guide }: an object whose key is the variable's name.[6] It is not a set. Python would read {Guide} as a set, so this one trips up Python developers. You'll see it everywhere, for example res.json({ guides }).
  • class A extends B is class A(B):.[7] As in Python, B can be any expression that produces a class, including a function call.
  • export default X marks the file's one main export. You import it without braces and can name it whatever you like. Named exports (export const GUIDE_MODULE) are imported with braces, using the exact name.[8]
  • Chaining (model.text().nullable()) works because each call returns an object you can keep calling methods on.

Using the module: the container

Here is a route that lists guides, at src/api/guides/route.ts:

import type { MedusaRequest, MedusaResponse } from "@medusajs/framework/http"
import { GUIDE_MODULE } from "../../modules/guide"

export const GET = async (req: MedusaRequest, res: MedusaResponse) => {
  const guideModuleService = req.scope.resolve(GUIDE_MODULE)
  const guides = await guideModuleService.listGuides()
  res.json({ guides })
}

This answers Lesson 1's open question. req.scope is the Medusa container, "a registry of Framework and commerce tools". resolve(name) hands back whatever is registered under that name.[9] You never write new GuideModuleService(): Medusa creates the service once at startup and gives it to you by name. Workflow steps, subscribers, and scheduled jobs get the same container, just under the name container.

The idea that matters for production: isolation

A module "can't access resources, such as services or data models, from other modules". Your Guide module can't resolve the Product module's service, and its data model can't hold a direct relation to Product's tables.[10]

So how do you build anything that crosses domains? Medusa gives you three tools:[10]

  • Module links associate records across modules, for example a guide with a product.
  • Query reads data across modules.
  • Workflows perform actions that span modules. Their steps resolve each module's service, and the workflow can roll back if a step fails.

A return touches orders, payments, and inventory, which are three modules. So it has to be a workflow. That's the start of your On-ramp learning gate, and the subject of Lesson 3.

Your roadmap applies the same rule one level up. Your agent never writes to Medusa's tables directly and only goes through its API. Each piece of data has exactly one owner, and the other parts ask that owner for changes.

Try it for real (optional)

This counts toward your On-ramp gate ("the throwaway project runs your custom module"). Build it in a throwaway folder outside goods, as the roadmap says.

  1. Check you have Node v20.19+ or v22.12+ and a running PostgreSQL, then run npx create-medusa-app@latest onramp-sandbox. Say no to the storefront for now.[11]
  2. Create the three module files above, then add { resolve: "./src/modules/guide" } to modules in medusa-config.ts.
  3. Run npx medusa db:generate guide and npx medusa db:migrate. Open the generated migration file and find your columns, including the three Medusa added for you.
  4. Add the route, run npm run dev, then curl http://localhost:9000/guides. Expect {"guides":[]}. It's empty because nothing creates guides yet. Lesson 3 fixes that with a workflow.

If anything breaks, paste the error into chat. Reading Medusa errors is part of the skill.
