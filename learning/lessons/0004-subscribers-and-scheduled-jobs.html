Events: the workflow announces what happened

Lesson 3's workflow ended with a step you haven't used yet:

emitEventStep({
  eventName: "guide.created",
  data: { id: guide.id },
})

emitEventStep comes from @medusajs/medusa/core-flows, and "it only emits the event after the workflow has finished successfully".[2] That rule matters. If a later step fails and the guide gets rolled back, nobody hears about a guide that doesn't exist. I checked this in your sandbox: the successful request logged Processing guide.created which has 1 subscribers. The ?simulate_failure=true request logged nothing.

Medusa's own workflows emit events the same way: order.placed, product.updated, and many more.[3] Medusa compares them to webhooks, except your handler lives inside the same codebase.

Notice the payload is just { id }. That's the convention. The subscriber fetches fresh data itself, so it never acts on a stale copy.

The subscriber

A subscriber is a file in src/subscribers/ that exports two things: the function to run, and a config naming the event.[3] This one is src/subscribers/guide-created.ts:

import type { SubscriberArgs, SubscriberConfig } from "@medusajs/framework"
import { GUIDE_MODULE } from "../modules/guide"
import GuideModuleService from "../modules/guide/service"

export default async function guideCreatedHandler({
  event: { data },
  container,
}: SubscriberArgs<{ id: string }>) {
  const logger = container.resolve("logger")
  const guideModuleService: GuideModuleService = container.resolve(GUIDE_MODULE)

  const guide = await guideModuleService.retrieveGuide(data.id)
  logger.info(`New ${guide.kind} guide: ${guide.title}`)
}

export const config: SubscriberConfig = {
  event: "guide.created",
}

The idea that matters for production: outside the flow

A subscriber runs after the workflow is done, separately from it. Medusa says subscribers are for "actions that aren't integral to the original flow", like a confirmation email after order.placed. "The subscriber has no impact on the original order-placement flow".[3]

Turn that around. If your subscriber throws, the guide still exists and the request still succeeded, because nothing is compensated. So the test is: if this fails, should the main change be undone? If yes, it's a step in the workflow. If no (an email, a sync, re-indexing a guide for your agent's search), it's a subscriber.

When a subscriber needs to change data, it should run a workflow, just as a route does: await someWorkflow(container).run({ input }). A subscriber is an entry point, not a place for business logic.

One more thing from your own server log: Local Event Bus installed. This is not recommended for production. In development, events travel in memory, so an event is lost if the process dies mid-way. In production you use the Redis Event Module.[3] That's a Setup 2 concern, and now you know what the warning means.

The scheduled job

A scheduled job is "an asynchronous function that the Medusa application runs at the interval you specify".[4] It's a file in src/jobs/, again with a default-exported function and a config. This one is src/jobs/count-guides.ts:

import type { MedusaContainer } from "@medusajs/framework/types"
import { GUIDE_MODULE } from "../modules/guide"
import GuideModuleService from "../modules/guide/service"

export default async function countGuidesJob(container: MedusaContainer) {
  const logger = container.resolve("logger")
  const guideModuleService: GuideModuleService = container.resolve(GUIDE_MODULE)

  const [, count] = await guideModuleService.listAndCountGuides()
  logger.info(`Guide report: ${count} guides in the database`)
}

export const config = {
  name: "count-guides",
  schedule: "* * * * *",
}
  • The function receives the container directly, with no wrapping object.
  • schedule is a standard cron expression, the same five fields as a Linux crontab: minute, hour, day of month, month, day of week. * * * * * is every minute, 0 0 * * * is midnight daily, and */15 * * * * is every 15 minutes. crontab.guru translates them.
  • listAndCountGuides() returns a pair: [guides, count]. const [, count] skips the first item and keeps the second, like Python's _, count = ....
  • To turn a job off, move the file out of src/jobs. Don't just delete the config export. That causes errors at build and start.[4]

This job only reads, so calling the service directly is fine, just as with Lesson 2's GET. For a job that changes data, such as a nightly ERP sync, Medusa's advice is to "create a workflow and execute it in a scheduled job".[4] Jobs only run while the Medusa application runs. They replace a cron entry or a Celery beat schedule, not a server that's switched off.

  • Template literals use backticks, with ${expression} inside. They're Python's f-strings. Plain quotes don't interpolate.[5]
  • Skipping in array destructuring: an empty slot before the comma skips that position.[6]
  • Nested destructuring in parameters: { event: { data } } reaches two levels into the argument and names only data. Here event isn't a variable, just the path to data.[6]

Try it for real

This completes your On-ramp gate. Paths are relative to ~/Documents/projects/onramp-sandbox/apps/backend. As in Lesson 3, the sandbox already contains both files above, which I ran to check this lesson.

  1. See the event. With npm run dev running, create a guide (the second curl from Lesson 3). Find Processing guide.created and your New sizing guide line in the server log.
  2. See no event. Repeat it with ?simulate_failure=true. Confirm that neither line appears.
  3. Prove it's outside the flow. Add throw new Error("subscriber broke") at the end of the subscriber. Create a guide. The request still returns 200 and GET /guides lists it. Then remove the line.
  4. Slow the job down. Change the schedule to every 5 minutes, and work out the expression yourself before checking it on crontab.guru.
  5. Write one yourself. Create src/subscribers/guide-missing-summary.ts from memory. It also listens to guide.created and logs a warning (logger.warn) when the new guide has no summary. Two subscribers on one event is fine. The log line will say has 2 subscribers.
