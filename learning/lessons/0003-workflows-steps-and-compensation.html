Workflows, steps, and compensation

Where the business logic lives, and why a return must be a workflow.

Win: write a workflow whose step undoes itself when a later step fails, and explain why that makes a return safer than a plain route.

Time: about 35 minutes, plus 30 minutes in your sandbox.

Why it matters: this is your On-ramp learning gate. Your agent's request_return tool will end in a Medusa workflow, and a half-finished return means a real customer is charged for something they sent back. Mission

Where workflows sit

  1. API routeHTTP entry point (Lesson 1)
  2. Workflowbusiness logic, step by step (today)
  3. Moduleowns one domain and its tables (Lesson 2)
  4. PostgreSQLthe database

In Lesson 2 the GET /guides route called the Guide module's service directly. That's fine for reading. For anything that changes data, Medusa's rule is: "You implement all custom flows within workflows, then execute them from API routes, subscribers, and scheduled jobs."[1] The route receives the request; the workflow decides what happens; the modules do the reading and writing.

The problem: a return in a plain route

Here is a return written the naive way. An API route can resolve any module's service from req.scope, so nothing stops you from writing this:

export const POST = async (req, res) => {
  const orders = req.scope.resolve("order")
  const payments = req.scope.resolve("payment")
  const inventory = req.scope.resolve("inventory")

  const ret = await orders.createReturn(...)       // 1. record the return
  await payments.refundPayment(...)                // 2. give the money back
  await inventory.adjustInventory(...)             // 3. put stock back on the shelf
  res.json({ return: ret })
}

(The method names are simplified to show the shape.) Now suppose step 3 throws because the warehouse location doesn't exist. Steps 1 and 2 have already happened. The customer has their refund and the return is recorded, but the stock count is wrong. Nobody gets told, and nothing puts things back. If step 2 had failed instead, the order would show a return with no refund behind it.

The problem isn't access: the route can reach all three modules. The problem is partial failure. Three separate modules means three separate writes, and nothing ties them together. A database transaction can't help either, because each module owns its own tables and may even talk to an outside system such as Stripe.

A workflow is a list of steps

Medusa defines a workflow as "a series of queries and actions, called steps, that complete a task". Unlike a plain function, a workflow tracks each step's progress, and it supports "roll-back logic for each step, so that you can handle errors gracefully and your data remain consistent across systems".[1]

You build one from two functions in @medusajs/framework/workflows-sdk:

PieceWhat it is
createStep(name, fn, compensate)One unit of work. fn does it; compensate undoes it.
new StepResponse(output, undoData)What a step returns. output goes to the workflow; undoData is saved for the compensation function.
createWorkflow(name, constructor)Lists the steps in order.
new WorkflowResponse(value)What the caller gets back as result.

If you've used Airflow or Celery chains in Python, this will feel familiar: you describe the tasks and their order, and an engine runs them and keeps track. The difference is the built-in undo.

The Guide workflow

This fills the gap from Lesson 2: something that creates guides. It lives in src/workflows/create-guide.ts. It has three steps: create the guide, a practice step that can fail on purpose, and an event (Lesson 4).

import {
  createStep,
  createWorkflow,
  StepResponse,
  WorkflowResponse,
} from "@medusajs/framework/workflows-sdk"
import { MedusaError } from "@medusajs/framework/utils"
import { emitEventStep } from "@medusajs/medusa/core-flows"
import { GUIDE_MODULE } from "../modules/guide"
import GuideModuleService from "../modules/guide/service"

type GuideData = {
  title: string
  kind: "sizing" | "care" | "compatibility"
  body: string
  summary?: string | null
}

type CreateGuideWorkflowInput = {
  guide: GuideData
  simulate_failure: boolean
}

export const createGuideStep = createStep(
  "create-guide",
  async (input: GuideData, { container }) => {
    const guideModuleService: GuideModuleService = container.resolve(GUIDE_MODULE)
    const guide = await guideModuleService.createGuides(input)
    return new StepResponse(guide, guide.id)
  },
  async (guideId: string, { container }) => {
    const guideModuleService: GuideModuleService = container.resolve(GUIDE_MODULE)
    await guideModuleService.deleteGuides(guideId)
  }
)

// Practice only: lets you trigger a failure after the guide exists.
const simulateFailureStep = createStep(
  "simulate-failure",
  async (input: CreateGuideWorkflowInput) => {
    if (input.simulate_failure) {
      throw new MedusaError(
        MedusaError.Types.NOT_ALLOWED,
        "Simulated failure after the guide was created"
      )
    }
    return new StepResponse()
  }
)

export const createGuideWorkflow = createWorkflow(
  "create-guide",
  (input: CreateGuideWorkflowInput) => {
    const guide = createGuideStep(input.guide)
    simulateFailureStep(input)
    emitEventStep({
      eventName: "guide.created",
      data: { id: guide.id },
    })
    return new WorkflowResponse(guide)
  }
)

Reading createGuideStep

1createStep(Makes a step. You'll call it inside a workflow.
2 "create-guide",A unique name. Medusa uses it to track the step.
3 async (input: GuideData, { container }) => {The step function. Second argument holds the container, the same one as req.scope.
4 ...container.resolve(GUIDE_MODULE)Get the Guide service by name, as in Lesson 2.
5 ...createGuides(input)Generated method. Writes one row.
6 return new StepResponse(guide, guide.id)Output for the workflow, then what the undo needs: just the ID.
7 },
8 async (guideId: string, { container }) => {The compensation function. Receives the second value from line 6.
9 ...deleteGuides(guideId)Undo: delete what line 5 created.
10 }

Medusa's docs describe it like this: "if a step creates a record, the compensation function deletes the record when an error occurs later in the workflow." It "only runs if an error occurs throughout the workflow".[2] The compensation never sees the step's full output, only what you pass as the second argument to StepResponse. So pass exactly what the undo needs.

What happens when a step fails

Send a request with ?simulate_failure=true, and this is the order of events (I ran it in your sandbox to check):

  1. create-guide runs. A new row is in the guide table.
  2. simulate-failure throws.
  3. Medusa runs the compensation of every step that already finished, newest first. Here that's only create-guide's, so the row is deleted.
  4. emitEventStep never runs, so no guide.created event goes out.
  5. .run() throws the error, and Medusa turns it into a response: {"type":"not_allowed", ...} with HTTP 400.

Afterwards, GET /guides doesn't show the guide and the database has no row for it. Either the whole workflow happens or none of it stays. This isn't a database transaction, though: compensation is ordinary code you write. If a step sends an email, its compensation can't unsend it, so put steps that can't be undone as late as possible.

The constructor describes, it doesn't run

The function you pass to createWorkflow looks like normal code, but it isn't run per request. Medusa calls it once to record the steps. "At that point, variables in the workflow don't have any values. They only do when you execute the workflow."[3] Writing an Airflow DAG file is the same idea: the file declares tasks, and the scheduler runs them later.

So guide on the first line of the constructor isn't a guide yet. It's a placeholder that means "the output of create-guide, once it exists". You can pass it on or read a property from it (guide.id), but you can't compute with it. Inside the constructor:[3]

Don'tDo instead
async constructor, awaitPlain function. Steps can be async; the constructor can't.
if, ternaries, ??, ||when(...).then(...) for branches, transform(...) for computed values
loops, ...spread, new Date()transform(...)
try/catchLet compensation handle failures

That's why the if lives inside simulateFailureStep. Inside a step function, ordinary code runs per request, so anything goes.

Calling it from the route

The route goes back to the shape you read in Lesson 1. Add a POST next to Lesson 2's GET in src/api/guides/route.ts:

import { createGuideWorkflow } from "../../workflows/create-guide"
import { PostGuideType } from "./validators"

export const POST = async (
  req: MedusaRequest<PostGuideType>,
  res: MedusaResponse
) => {
  const { result } = await createGuideWorkflow(req.scope).run({
    input: {
      guide: req.validatedBody,
      simulate_failure: req.query.simulate_failure === "true",
    },
  })
  res.json({ guide: result })
}

And Lesson 1's Zod schema, in src/api/guides/validators.ts:

import { z } from "zod"

export const PostGuideSchema = z.object({
  title: z.string(),
  kind: z.enum(["sizing", "care", "compatibility"]),
  body: z.string(),
  summary: z.string().nullable().optional(),
})

export type PostGuideType = z.infer<typeof PostGuideSchema>

It's attached in src/api/middlewares.ts with { method: ["POST"], matcher: "/guides", middlewares: [validateAndTransformBody(PostGuideSchema)] }. Now the request passes three checks in order. Zod checks the shape (a kind of "weather" gets a 400 before any workflow runs). The workflow applies the business rules. The database enforces the constraints (Lesson 2's check on kind).

Back to the return

As a workflow, the return becomes three steps, and each step can undo itself. The refund moves to the end: money sent through Stripe is the hardest thing to take back, so it only runs once everything else has worked.

StepDoesCompensation
1. create returnOrder module records the returnCancel the return
2. restockInventory module adjusts stockReverse the adjustment
3. refundPayment module refunds via StripeNone needed: nothing runs after it

If the refund fails, Medusa reverses the restock, then cancels the return. The order ends up as if nothing happened, and the customer gets an error instead of a half-finished return. You won't write this one yourself: Medusa's own order and return flows are already built as workflows in @medusajs/medusa/core-flows, the same package emitEventStep comes from. Your agent's tools will call Medusa's API routes, and those run the workflows.

The learning gate, in one paragraph

A plain route runs its writes one after another. If a later write fails, the earlier ones stay, and the data across modules no longer agrees. A workflow records each step as it completes. When one fails, it runs the completed steps' compensation functions in reverse order, so the change happens completely or gets undone. Medusa also tracks every step's progress, so you can see where it failed. Practise saying this from memory. It's what the learning gate asks for.

Four new pieces of TypeScript

Python

kind: Literal["sizing", "care"]

class GuideData(TypedDict):
    summary: NotRequired[str | None]

raise ValueError("bad")

if a == "true": ...

TypeScript

kind: "sizing" | "care"

type GuideData = {
  summary?: string | null
}

throw new Error("bad")

if (a === "true") { ... }
  • "sizing" | "care" is a union of string literals, like Python's Literal[...]. Only those exact strings type-check.[4] Like every type, it's erased at runtime, which is why Zod's z.enum repeats the list.
  • summary?: marks a key that may be missing. | null says it may also be present but null. They're different, just as in Python a missing key differs from None.
  • throw new X(...) is raise X(...). In JavaScript you need new to create an instance of a class.[5]
  • === is the equality you want. The older == converts types first (1 == "1" is true), so always use three equals signs.[6] Query strings are always text, which is why the route compares against "true" and not true.

Stuck on step 4? One possible answer 
type FillSummaryInput = { id: string; body: string; summary?: string | null }

export const fillSummaryStep = createStep(
  "fill-summary",
  async (guide: FillSummaryInput, { container }) => {
    const guideModuleService: GuideModuleService = container.resolve(GUIDE_MODULE)
    const summary = guide.summary ?? guide.body.split(".")[0]
    const updated = await guideModuleService.updateGuides({ id: guide.id, summary })
    return new StepResponse(updated, { id: guide.id, summary: guide.summary ?? null })
  },
  async (previous: { id: string; summary: string | null }, { container }) => {
    container.resolve("logger").info("Undoing fill-summary")
    const guideModuleService: GuideModuleService = container.resolve(GUIDE_MODULE)
    await guideModuleService.updateGuides(previous)
  }
)

// in the workflow constructor:
const guide = createGuideStep(input.guide)
const withSummary = fillSummaryStep(guide)
simulateFailureStep(input)
// ... and return new WorkflowResponse(withSummary)

?? is fine here because it's inside a step function, which runs per request. It would not be allowed in the constructor.
