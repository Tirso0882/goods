The code

This is the handler from Medusa's own customization tutorial. It lets an admin create a "brand". It lives at src/api/admin/brands/route.ts.[1]

import {
  MedusaRequest,
  MedusaResponse,
} from "@medusajs/framework/http"
import {
  createBrandWorkflow,
} from "../../../workflows/create-brand"

type PostAdminCreateBrandType = {
  name: string
}

export const POST = async (
  req: MedusaRequest<PostAdminCreateBrandType>,
  res: MedusaResponse
) => {
  const { result } = await createBrandWorkflow(req.scope)
    .run({
      input: req.validatedBody,
    })

  res.json({ brand: result })
}

You only need four ideas to read it.

1. Imports and exports

Python (imaginary package)

from medusa.framework.http import (
    MedusaRequest,
    MedusaResponse,
)
from ...workflows.create_brand import (
    create_brand_workflow,
)

TypeScript

import {
  MedusaRequest,
  MedusaResponse,
} from "@medusajs/framework/http"
import {
  createBrandWorkflow,
} from "../../../workflows/create-brand"

The names come first and the source comes after from, which is the reverse of Python's order. A source starting with . or .. is a file path relative to the current file. Medusa's examples leave out the .ts extension. Any other source is a package from node_modules.[2] JavaScript names use camelCase where Python uses snake_case.

Python makes every top-level name importable. JavaScript doesn't: a file only shares what it marks with export. Medusa uses this. It finds your handler by its exported name (POST handles POST requests) and builds the URL from the file's path under src/api. There is no decorator and no central routes file.[3]

2. Types are hints that disappear

You already know this idea from Python. Type hints like name: str are checked by a tool such as mypy, and ignored when the code runs. TypeScript works the same way. The compiler checks your types, then deletes them to produce plain JavaScript. The TypeScript handbook says annotations "never change the runtime behavior of your program".[4]

Python

class PostAdminCreateBrandType(TypedDict):
    name: str

req: MedusaRequest[PostAdminCreateBrandType]

TypeScript

type PostAdminCreateBrandType = {
  name: string
}

req: MedusaRequest<PostAdminCreateBrandType>
  • type X = { ... } gives a name to an object's shape, like a TypedDict.[5]
  • MedusaRequest<T> is a generic: angle brackets where Python uses square ones, as in list[str]. Here it tells the editor what shape the request body has.[6]
  • string, number, boolean are the basic types. There is no separate int and float.
  • You'll often see import type { ... }. It's the same as a normal import, but it can only bring in types, so the whole line is deleted at compile time.[7]

3. Async arrow functions

Python

async def POST(req, res):
    ...

TypeScript

export const POST = async (req, res) => {
  ...
}

(params) => { body } is an arrow function: a function written as a value and stored in a name.[8] Putting async in front works like async def: inside it you can await things, and calling it gives you back a Promise, which plays the role of Python's coroutine.[9] Curly braces mark the body where Python uses indentation.

const means the name can't be pointed at something else later. The object it holds can still change.[10] Use let for names you do reassign.

4. Destructuring and object literals

Python

output = await create_brand_workflow(
    req.scope
).run(input=req.validated_body)
result = output["result"]

res.json({"brand": result})

TypeScript

const { result } = await createBrandWorkflow(
  req.scope
).run({ input: req.validatedBody })


res.json({ brand: result })

const { result } = obj is destructuring. It pulls the result key out of an object and stores it in a variable with the same name.[11] Python has nothing exactly like it for dicts. Python's tuple unpacking matches by position, while object destructuring matches by key name.

JavaScript has no keyword arguments. Libraries take one object instead, so .run({ input: ... }) is Medusa's version of .run(input=...). Keys in an object literal don't need quotes.

The idea that matters for production

Go back to idea 2. The type PostAdminCreateBrandType no longer exists when the server runs. If a client posts {"name": 42}, no TypeScript type will stop it.

That's why the same tutorial adds a Zod schema and a validation middleware. Zod checks the JSON at runtime and fills req.validatedBody only when the body passes.[1] z.infer<typeof Schema> then derives the TypeScript type from the schema, so you write the shape once.[12]

export const PostAdminCreateBrand = z.object({ name: z.string() })
type PostAdminCreateBrandType = z.infer<typeof PostAdminCreateBrand>

Zod is to TypeScript what Pydantic is to Python. Your agent faces the same problem on the Python side: tool arguments written by the model are untrusted JSON, just like a request body. You will validate them with Pydantic for the same reason.
